## بيئة العرض

استخدم قاعدة Demo مستقلة ومطبّقًا عليها migrations القائمة وإعدادات README، مع `Demo__SeedProfile=Football` (الافتراضي). الأكاديمية المحجوزة `30000000-0000-0000-0000-000000000003`، slug `football-demo`. تشغيل عادي على قاعدة موجودة لا يحذف أي أكاديمية قديمة ولا يعيد بيانات معدّلة؛ الحسابات أدناه تنتمي لأكاديمية العرض فقط. الأفضل قاعدة جديدة للعرض النظيف. `LegacyRegression` يُستخدم صراحة في اختبارات الويب/backend متعددة الرياضات والعزل، ولا يُزرع تلقائيًا في العرض.

تاريخ العرض `Demo__ReferenceDate=2026-09-28`. رياضة كرة القدم فقط؛ الفروع: **فرع مدينة نصر، فرع مدينتي، فرع الشروق**. seed الابتدائي: 6 مجموعات مواليد 2018–2013، 4 مدربين بحسابات وهواتف منفصلة، 30 لاعبًا بأكواد `FB-0001`–`FB-0030`، و29 ولي أمر بروابط صريحة. 10 اشتراكات نشطة بعيدة عن الانتهاء، 10 تنتهي قريبًا و10 منتهية؛ 30 تحصيلًا وإيصالًا، دفع معلق وآخر فاشل، 24 جلسة و90 سجل حضور لاعب و18 حضور مدرب، 30 تقييمًا منشورًا ومسودة. هذه أرقام البداية لا وعد بإعادتها بعد التجربة؛ تتغير المؤشرات من السجلات عند تنفيذ الإجراءات، ولا تستخدم hardcoded dashboard totals.

رحلة الويب: المالك ← لوحة المالك ← اللاعبون/الفروع/المجموعات ← المدربون ← إضافة مدرب. الاسم والهاتف إلزاميان؛ البريد والإسناد اختياريان. إنشاء المدرب يحفظ الهوية والعضوية والإسناد ذريًا، ويتيح OTP للموبايل عند نشاط الحساب. لا كلمة مرور مشتركة ولا تغيير لهوية موجودة. نفس الهاتف normalized يعيد استخدام الهوية فقط عند تطابق البيانات؛ أي اختلاف يتطلب مراجعة ولا يكشف بيانات الأكاديمية الأخرى. تكرار الحفظ المطابق لا يكرر العضوية. لإدارة الإسناد لاحقًا استخدم «إسناد مجموعة» القائمة.

رحلة Guardian Flutter: onboarding عند التشغيل الأول ← هاتف/OTP ← الرئيسية الداكنة والأبناء وقوة آخر تقرير ← وجبات اليوم والموعد القادم ← ملف الطفل/التقرير/الطب/المعرض ← اختيار باقة وتسجيل/تجديد. التحويل اليدوي يعرض الحسابات المضبوطة من المالك ثم يرفع إثباتًا؛ يظل الطلب بانتظار القبول. محاكاة الدفع الداخلية تبقى في Demo فقط. تجديد الغير يبدأ باسم لاعب، ثم مرجع مشفر مرتبط بالدافع ينتهي بعد عشر دقائق، ولا يضيف الطفل للحساب. الخادم يحسب المال والاشتراك والتقييم؛ الكتابة idempotent بلا إعادة آلية.

Coach: مجموعات نشطة مسندة ← تفاصيل اللاعبين والحضور والتقييم ← رفع صور/فيديو للمجموعة، مع وصول أولياء الأمور المرتبطين فقط. Owner: طلبات الدفع أولًا وتقسيم أنواعها ← تحصيل نقدي/إلكتروني وفترة/فرع ← تقارير؛ الاعتماد وإسناد المجموعة من الويب. حساب كل دور يتيح Dark/Light وعربي/English. المسارات الخاصة تزول مع logout/تبديل العضوية. SMS الحقيقي غير متوفر؛ خارج Demo يرجع `501`.

## إعادة تهيئة آمنة — DM-12

**أوقف API العرض قبل reset. هذا يمحو تعديلات العرض داخل الأكاديمية المحجوزة فقط ويعيد seed؛ لا يمس الأكاديميات الأخرى أو الهويات العامة.** نفّذ من جذر المشروع مع connection محلي مؤكد وDemo environment محمّلين مسبقًا، وليس production:

```bash
Demo__ResetConfirmation=football-demo-only dotnet run \
  --project apps/api/src/Academy.Api --no-launch-profile -- --reset-football-demo
```

العملية تتطلب `Demo` و`SeedEnabled=true` وprofile `Football`، وثلاث علامات متطابقة مخزنة: ID المحجوز + slug + `EnglishName=Football Demo Dataset v1`، إضافة إلى التأكيد الصريح. إذا لم يسبق seed أو تغيّرت العلامة ترفض العملية. لا يقبل الأمر AcademyId اختياريًا ولا ينفذ drop/truncate. داخل transaction وقفل advisory: يلغي جلسات الويب/native المرتبطة بأكاديمية العرض، يحذف سجلاتها التابعة بترتيب FK، ثم يعيد المعرفات والسجلات المحددة. فشل أي خطوة يرجع العملية كلها. بدء API المعتاد ليس reset.

تبقى `Users` وكلمات المرور/security stamps كما هي لحماية أي عضوية في أكاديمية أخرى؛ المدرب المضاف يدويًا يفقد عضويته في ديمو العرض بعد reset، لكن هويته العامة لا تُحذف. لذلك التكرار deterministic للسجلات الخاصة بأكاديمية العرض، وليس وعدًا بمحو كل هوية/OTP عالمية. أي تضارب مع هوية محجوزة يرفض دون استبدال. لا يُستخدم reset لتطبيق migrations؛ سبع migrations مراجعة المالك إضافية موثقة في STATUS.

## رحلة مراجعة المالك وحدودها

- أنشئ لاعبًا من الويب مع باقة ومجموعة وتحصل فعليًا؛ تحقق من الملف والصورة والفترة وإيصال التحصيل. دون دفع مؤكد لا يصبح الملف اشتراكًا نشطًا.
- عرض الإخوة 20% افتراضيًا؛ تغيير المالك للنسبة والمخزون يبقيهما كما عدلهما عند إعادة التشغيل، ولا يحدث reset أو إعادة تعبئة تلقائية. قيم المنتج اصطناعية ولا تمثل دفعًا حقيقيًا.
- اضبط حساب تحويل **Demo فقط** من طلبات الدفع في الويب إن أردت اختبار النسخ/الإثبات؛ النظام لا يختلق حساب بنك أو يؤكد التحويل من الصورة. قبول واحد يحفظ التحصيل والفترة والمجموعة والإشعار.
- أخبار منشورة تظهر خلال المدة المختارة وتختفي عند انتهاء المدة؛ عدم وجود أخبار لا يعرض صندوقًا فارغًا. وسائط المجموعة تحفظ جمهورها وقت الرفع؛ اللاعب الذي يلتحق لاحقًا لا يرث الوسائط القديمة.
- التغذية معلومات واقتراحات عامة فقط، وقيم الحصص تقديرية وليست وصفة أو علاجًا؛ [المصادر](../nutrition/YOUTH_FOOTBALL_NUTRITION_DEMO_DATA.md). لا سعر أو طلب أو checkout للتغذية.
- رحلات التكامل تغير سجلاتها؛ شغّلها على قاعدة اختبار منفصلة لا قاعدة المراجعة اليدوية. المنفذ المحلي الحالي للمراجعة `5080`، والاختبارات المعزولة تستخدم `5280`؛ عنوان API يمرر صراحة إلى Flutter.

بناء iOS Simulator متاح، وليس إصدار متجر. Android SDK غير مثبت محليًا ولم يُختبر Android. SMS/push والدفع الحقيقي وApple Pay والتوقيع والمتاجر وتخزين الوسائط الدائم وفحصها بوابات لاحقة. **NOT PRODUCTION READY**؛ نتيجة Demo النهائية في STATUS فقط.
